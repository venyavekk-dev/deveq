# AGENTS.md

Общие правила работы с пользователем во всех проектах. Правила конкретного проекта дополняют эти инструкции, а не заменяют их.

## Перед началом работы

- Прежде чем писать код, кратко изложить план: что будет сделано и почему. Если задача неясна — задать уточняющие вопросы.
- Не начинать реализацию, пока пользователь явно не подтвердил план: «ок», «давай», «мёржи» и т. п.
- Применять это правило к любой задаче с кодом, а не только к разовым правкам.

## Git, worktree и Vercel

- Для новой задачи создавать ветку от основной ветки репозитория, обычно `main`. Использовать имя `codex/<короткое-название>`.
- Для любой задачи, которая изменяет файлы в существующем Git-репозитории, по умолчанию создавать отдельный `git worktree` от актуальной удалённой основной ветки. Общую рабочую папку использовать только для чтения, если пользователь явно не разрешил редактировать её.
- Перед созданием worktree проверять `git status`, текущую ветку, remotes и список worktree. Для каждой задачи использовать отдельный путь и уникальную ветку.
- Не переключать ветки и не использовать `git stash`, `git reset`, `git clean`, `git checkout --` или аналогичные команды в общей рабочей папке, чтобы подготовить её к задаче.
- Если репозиторий ещё не имеет первого коммита или задача должна продолжить конкретные незакоммиченные изменения пользователя, сначала согласовать безопасный способ работы. Не переносить и не коммитить такие изменения без разрешения.
- Не удалять worktree, пока в нём есть незакоммиченные или неотправленные изменения.
- Делать небольшие осмысленные коммиты по ходу работы, а не один большой коммит в конце.
- Самостоятельно создавать pull request через `gh pr create` и писать его заголовок и описание: что изменено, зачем и как проверить.
- При создании pull request явно указывать `--head <ветка> --base <основная>`, не полагаясь на текущую ветку рабочей папки.
- Если репозиторий подключён к Vercel, после открытия pull request присылать ссылку на превью из комментария Vercel-бота. Повторно присылать актуальную ссылку после каждого нового коммита в этом pull request.
- Превью может быть закрыто Vercel Auth или SSO. Проверять результат через сборку, lint, typecheck и `curl`, не полагаясь только на прямой доступ к превью.
- Сливать pull request в основную ветку только после явного разрешения пользователя в чате на этот конкретный pull request.
- Если изменение рискованное, неоднозначное или превью не собралось — сначала показать пользователю состояние и не выполнять слияние вслепую.
- Перед Git-командами проверять фактически выбранную ветку и путь текущего worktree.

## Стиль работы

- Делать небольшие целевые изменения без несвязанного рефакторинга.
- Не менять дизайн и визуальные решения без явного запроса.
- Самостоятельно разрешать конфликты слияния и показывать готовый результат.
- Не открывать и не запускать браузер без отдельного явного разрешения пользователя каждый раз. Использовать dev-сервер и текстовые проверки вместо браузера.
- Переиспользовать уже запущенный dev-сервер и не перезапускать его без необходимости.
- Объяснять простым языком. Использовать технические подробности по запросу или когда они необходимы для объяснения проблемы.
- Задавать уточняющие вопросы на русском языке.

## Типографика

Весь пользовательский текст в чате и контенте должен быть отипографлен:

- использовать длинное тире «—», а не дефис, где это грамматически уместно;
- использовать «ёлочки» в русском тексте и “curly quotes” в английском;
- использовать неразрывные пробелы перед короткими предлогами и союзами, между инициалами и фамилией, перед единицами измерения и в других подходящих местах.
